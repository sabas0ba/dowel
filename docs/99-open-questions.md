## Q1. `cfg` 名前空間の語彙

**状態**: 未着手。次に詰めるべき項目。

`dowel.toml` の `when` 述語、`dowel.build` の `match` / `when`、
ツールチェーン選択、ABI ラベルのすべてが参照する共通基盤。

暫定案:

```
cfg.opt        構成（debug / release / …）
cfg.target     ターゲットトリプル
host.os        ビルドホストの OS
host.arch      ビルドホストのアーキテクチャ
feature.<name> 機能フラグ
tc.c           選択された C ツールチェーン
```

決めるべき点:

- `cfg` に含める次元の確定（これが ABI ラベルの構成要素の候補になる）
- 述語の合成規則（暗黙の AND 以外を許すか）
- 語彙を固定するか、ツールチェーンが拡張できるようにするか

### 実装が用いている暫定語彙

実装を進めるために、上記の暫定案をそのまま**閉じた語彙**として実装してある
（`crates/dowel-eval/src/config.rs`）。これは Q1 の決定ではなく、
決定までの仮置きである。現物は `dowel schema dump --section=cfg` で得られる。

| 名前空間 | 実装済みのキー | 値域 |
|---|---|---|
| `cfg` | `opt` | `debug` / `release` |
| `cfg` | `target` | ターゲットトリプル（自由文字列） |
| `host` | `os` / `arch` | ビルドホストの値 |
| `feature` | `<name>` | 真偽（`dowel.toml` の `[features]` で宣言されたもののみ） |
| `tc` | `c` | 選択された C ツールチェーンの識別子 |

述語の合成は暗黙の AND のみ。`match` の網羅性検査は値域が有限な
`cfg.opt` / `host.os` / `host.arch` に対してのみ働き、`cfg.target` は
値域が無限であるため `_` アームを必須とする。この非対称は Q1 の決定時に見直す。

## Q2. ABI ラベルの構成

Conan の `package_id` に相当する。粒度の設計が全体を左右する。

`_GLIBCXX_USE_CXX11_ABI`、MSVC ランタイム種別、サニタイザ、LTO、例外モデル、
浮動小数点モデル。

Phase 0 の検証（実在する不整合の検出数）が、この設計の必要粒度を示す。

## Q9. ストアに値を格納する際の `FileId` の扱い

**状態**: 未着手。ストアへの値の格納に着手する時点で決める。

ストアの容れ物と、`Session` からの接続は実装済みである
（[91-implementation-status.md](91-implementation-status.md)）。
残るのは値そのものの格納であり、そこで `FileId` の扱いが問題になる。

`FileId` は `SourceMap` 内の添字であり、読み込んだ順に振られる。
プロセス内では [`SourceMap::load`](../crates/dowel-support/src/source.rs) が
パスに対して同じ識別子を返すため安定しているが、**プロセスを跨ぐと
読み込み順に依存する**。パッケージの走査順が変われば別の番号になる。

格納する値（`Document` / `Value` / `Prov`）はスパンを含み、スパンは
`FileId` と対でしか意味を持たない。番号がずれた状態で値を復元すると、
来歴と診断が別のファイルを指す。

選択肢:

- パスを鍵として `FileId` の対応表をストアに持ち、復元時に振り直す
- 値の中の `FileId` をパスに置き換えて格納し、復元時に引き直す
- `FileId` をパスのハッシュにして、読み込み順から独立させる

3案目は `SourceMap` の添字としての性質を失うため、参照の経路が増える。
1案目が有力だが、対応表の更新と値の無効化の関係（ファイルが消えた場合、
その `FileId` を指す値をどう扱うか）が未定。

併せて決めるべき点:

- 直列化の形式（`Document` は約40の型を含む。形式の版とその互換規則）
- 格納の単位（ファイル単位か、ターゲット単位の派生まで待つか）
