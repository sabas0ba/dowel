# テストスイートの設計

[50-development.md](50-development.md) は開発環境と規約を扱う。本文書は
**何をどう検査するか**を扱う。

## 方針

各層に「答える問い」を1つだけ持たせる。同じ問いを2つの層で答えない。
重複した検査は、壊れたときに直す場所を増やすだけで、壊れる範囲を狭めない。

| 層 | 問い | 場所 | 段階名 |
|---|---|---|---|
| 単体 | 部品は仕様どおりか | `crates/*/src/**` の `mod tests` | `unit-*` |
| 頑健性 | 壊れた入力で落ちないか、不変量は保たれるか | `crates/dowel-syntax/tests/robustness.rs` | `syntax-robustness` |
| 統合 | 層をまたいだ組み上げは正しいか | `crates/dowel-model/tests/` | `model-*` |
| e2e | 生成したグラフを実行すると本当に動くか | `crates/dowel-cli/tests/e2e.rs` | `e2e` |
| **シナリオ** | 時間をまたぐ操作列で正しく振る舞うか | `crates/dowel-cli/tests/scenario.rs` | `scenario` |
| **実物** | 現実の形のプロジェクトが通るか | `tests/projects/` | `fixture` |
| **診断と網羅** | 診断が利用者まで届くか。機能に対しテストがあるか | `crates/dowel-cli/tests/diagnostics.rs` | `diagnostics` |
| 例 | 文書に載せた例が動くか | `crates/dowel-cli/tests/example.rs` | `example` |
| **文書** | リンクが切れていないか。索引に漏れが無いか | `crates/dowel-cli/tests/docs.rs` | `docs` |
| 計測 | 予算内か | `scripts/measure-startup.py` | `startup` |

入口は1つ（`make verify`）。ローカルでも CI でも同じものを実行する。

## 新しい3層をなぜ足したか

### 実物（`tests/projects/`）

合成した2パッケージのプロジェクトは、意味論を1つずつ切り出して確かめるには良い。
しかし現実のプロジェクトが持つ形を持たない。

- 依存が3層以上あり、公開と非公開が混ざる
- ダイヤモンド（同じライブラリへ2経路で到達する）
- **どのパッケージも公開ヘッダを `include/` に置く**という慣習

最後のものは特に重要である。この層を入れた最初の実行で、
「相対パスだけで重複を判定していたため、依存が2段を超えると
別パッケージのインクルードディレクトリが消える」という欠陥が出た。
2パッケージの合成プロジェクトでは、経路が1段しかないため決して現れない。

**フィクスチャは自分自身を検査する。** ビルドシステムの意味論に対する主張は、
可能な限りフィクスチャ側の C に `#error` と終了状態で書く。利用者が実際に
確かめる形と同じであり、期待値をハーネス側と二重に持たなくて済む。
C から観測できないもの（`compile_commands.json` の中身、伝播しないことの否定、
再ビルドで何が走ったか）だけをハーネスに書く。

規約は [`tests/projects/README.md`](../tests/projects/README.md) にある。

### シナリオ（`scenario.rs`）

ビルドシステムの価値の大半は2回目以降の実行にある。しかし e2e が見るのは
1回の実行であり、単発の実行をいくら並べても「編集して、また実行して」という
経路は検査できない。

この層を入れた最初の実行で、
「direct 実行器はコマンド列を最新性の判定に入れていないため、
フラグを変えた再ビルドを取りこぼす」という欠陥が出た。
入力もその更新時刻も変わらないためであり、結果は古いフラグで作られた成果物が
**成功として報告される**状態だった。

観測は `--executor=direct --log-level=debug` の判定理由による。
成果物の更新時刻を見る方法もあるが、時刻の分解能に依存し、
「なぜ再実行したか」が記録に残らない。

### 文書（`docs.rs`）

文書は腐る。腐っても誰も落ちないため、腐ったまま残る。ここは
「腐ったら落ちる」機構である。

検査するのは機械的に判定できるものだけであり、内容が正しいかは見ない。

- 相対リンクの指す先が存在すること
- **コードとスクリプトが名指しする文書が存在すること** — 番号を付け替えたとき、
  本文中のリンクより先にここが切れる。書式を持たないため別に拾う
- `docs/README.md` の一覧が `docs/` の中身と一致すること
- `docs/adr/README.md` の表が ADR の実体と一致すること（双方向）

### 診断と網羅（`diagnostics.rs`）

単体テストは「その関数が診断を作ること」を見る。しかし利用者に届くまでには
評価・検証・整形・出力の経路があり、途中で握り潰されても単体テストは通る。

この層を入れた最初の実行で、`invalid-source` と `unresolved-path` の2つが
**一度も到達しない**ことが分かった。ディレクトリを `sources` に書くと
リンカの `input file unused` になり、存在しないファイルを書くと
ninja の `no known rule` になっていた。どちらもマニフェストのどの行が
原因かを示さない。

網羅はこのファイル自身が追う。診断コードを対象にするのは、利用者に見える表面の中で
唯一、安定識別子を持ち機械的に数え上げられるためである。
ソースを走査して見つけたコードが事例表に無ければ落ちる。
書けないものは `UNCOVERED` に**理由つきで**置く。理由を書けないなら、
それは事例を書けるということである。

この検査が保証するのは網羅の**下限**であって、事例が意味のある入力かどうかは
見ない。そこは各事例の `why` を人が読んで判断する。

## テストを足すときの判断

| 何を確かめたいか | 置く場所 |
|---|---|
| 関数・データ構造の振る舞い | 当該クレートの `mod tests` |
| 壊れた入力への耐性 | `robustness.rs` |
| 複数の層をまたぐ組み上げ | `crates/dowel-model/tests/` |
| コンパイラに渡る引数、実際に動く成果物 | `e2e.rs` |
| 編集してからの再実行、構成の切り替え、テストの再実行 | `scenario.rs` |
| 現実の依存形状でしか出ない性質 | `tests/projects/` に新しいフィクスチャ |
| 新しい診断 | `diagnostics.rs` の事例表（足さないと網羅検査が落ちる） |
| 新しい文書 | `docs/README.md` の一覧（足さないと文書検査が落ちる） |

## 規約

- **テスト名は主張を述べる。** `test_build` ではなく
  `editing_one_source_recompiles_only_that_object` と書く。
  落ちたときに、名前だけで「何が壊れたか」が分かる状態にする
- **数え上げで押さえる。** 増分の検査は「値が正しい」だけでは足りない。
  何を計算しなかったかが要点であり、そこは回数でしか観測できない
- **一時ファイルはリポジトリ外に作らない。** `target/` 配下に置く
  （`/tmp` を使わない理由は [50-development.md](50-development.md) 5節）
- **現物は汚さない。** `examples/` と `tests/projects/` は
  `target/` へ複製してからビルドする。汚れた場合は
  `every_fixture_is_left_clean_in_the_repository` が検出する
- **コード中の定義は英語。** 説明は日本語でよい
  （[50-development.md](50-development.md) 5節）
