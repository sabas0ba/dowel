# テストスイートの設計

[50-development.md](50-development.md) は開発環境と規約を扱う。本文書は
検査の対象と方法を扱う。

## 方針

各層に検査対象を1つだけ割り当て、同じ対象を複数の層で検査しない。
検査が重複すると、変更時の修正箇所が増える一方で検出範囲は広がらない。

| 層 | 問い | 場所 | 段階名 |
|---|---|---|---|
| 単体 | 各部品が仕様どおりか | `crates/*/src/**` の `mod tests` | `unit-*` |
| 頑健性 | 壊れた入力に対する耐性と不変量の保持 | `crates/dowel-syntax/tests/robustness.rs` | `syntax-robustness` |
| 統合 | 層をまたいだ組み上げの正しさ | `crates/dowel-model/tests/` | `model-*` |
| e2e | 生成したグラフの実行結果 | `crates/dowel-cli/tests/e2e.rs` | `e2e` |
| シナリオ | 時間をまたぐ操作列での振る舞い | `crates/dowel-cli/tests/scenario.rs` | `scenario` |
| フィクスチャ | 実プロジェクトの形状でのビルドと実行 | `tests/projects/` | `fixture` |
| 診断と網羅 | 診断が利用者に到達するか。機能に対する検査の有無 | `crates/dowel-cli/tests/diagnostics.rs` | `diagnostics` |
| 例 | 文書に記載した例の動作 | `crates/dowel-cli/tests/example.rs` | `example` |
| 文書 | リンクが解決するか。索引が完全か | `crates/dowel-cli/tests/docs.rs` | `docs` |
| 計測 | 予算の遵守 | `scripts/measure-startup.py` | `startup` |

入口は1つ（`make verify`）。ローカルでも CI でも同じものを実行する。

## 後から追加した3層

### フィクスチャ（`tests/projects/`）

合成した2パッケージのプロジェクトは、意味論を個別に検査する用途には適するが、
実際のプロジェクトが持つ依存形状を持たない。

- 依存が3層以上あり、公開と非公開が混ざる
- ダイヤモンド（同じライブラリへ2経路で到達する）
- どのパッケージも公開ヘッダを `include/` に置くという慣習

3点目に起因して、この層を追加した最初の実行で欠陥を検出した。併合が相対パスのみで
重複を判定していたため、依存が2段を超えると別パッケージのインクルードディレクトリが
除去されていた。2パッケージの合成プロジェクトでは経路が1段のため発現しない。

フィクスチャは自身を検査する。ビルドシステムの意味論に対する検査は、可能な限り
フィクスチャ側の C に `#error` と終了状態で記述する。利用者が実際に用いる形式と
同一であり、期待値をハーネス側と重複して保持せずに済む。C から観測できない項目
（`compile_commands.json` の内容、伝播しないことの検査、再ビルドの実行対象）のみを
ハーネス側に記述する。

規約は [`tests/projects/README.md`](../tests/projects/README.md) にある。

### シナリオ（`scenario.rs`）

ビルドシステムの主要な機能は2回目以降の実行にある。e2e が検査するのは
1回の実行であり、単発の実行を並べても、編集と再実行を繰り返す経路は検査できない。

この層を追加した最初の実行で、direct 実行器がコマンド列を最新性の判定に
含めていないため、フラグ変更後の再ビルドが実行されない欠陥を検出した。
入力もその更新時刻も変わらないためである。結果として、変更前のフラグで
生成された成果物が成功として報告されていた。

観測は `--executor=direct --log-level=debug` の判定理由による。
成果物の更新時刻を見る方法もあるが、時刻の分解能に依存し、
「なぜ再実行したか」が記録に残らない。

### 文書（`docs.rs`）

文書の不整合はビルドにもテストにも影響しないため、検査しない限り検出されない。

対象は機械的に判定できる項目に限る。記述内容の妥当性は検査しない。

- 相対リンクの指す先が存在すること
- コードとスクリプトが参照する文書が存在すること。文書番号を変更した場合、
  Markdown のリンクより先にこちらが解決しなくなる。書式を持たないため別途走査する
- `docs/README.md` の一覧が `docs/` の中身と一致すること
- `docs/adr/README.md` の表が ADR の実体と一致すること（双方向）

### 診断と網羅（`diagnostics.rs`）

単体テストは診断が生成されることを検査する。しかし利用者に到達するまでには
評価・検証・整形・出力の経路があり、途中で破棄されても単体テストは成功する。

この層を追加した最初の実行で、`invalid-source` と `unresolved-path` の2つが
到達不能であることを検出した。ディレクトリを `sources` に記述するとリンカの
`input file unused` が、存在しないファイルを記述すると ninja の `no known rule` が
出力されていた。いずれもマニフェストの原因箇所を示さない。

網羅の追跡は同一ファイルで行う。診断コードを対象とするのは、利用者に見える
インタフェースのうち、安定識別子を持ち機械的に列挙できる唯一の対象であるためである。
ソースを走査して検出したコードが事例表に無い場合、検証が失敗する。
事例を記述できない項目は `UNCOVERED` に理由とともに記載する。

この検査が保証するのは網羅の下限であり、事例が妥当な入力かどうかは検査しない。
その判断は各事例の `why` の記述による。

コードの網羅は診断の内容を見ない。併合の衝突（`merge-conflict` /
`abi-mismatch`）は2つのパッケージから到達した値を対にして報告するが、
人間向けの描画が主ラベルのファイルしか出していなかった。機械可読形式には
両方の位置があるため、構造を見る単体テストでは成功する。現在は事例表に
2パッケージの入力を置き、両方のファイル名が描画に現れることを検査する。

同じく、事例表は修正提案の存在しか見ない。範囲の誤りは適用して初めて現れるため、
提案を書き戻してもう一度 `check` を掛ける検査を併せて置く。判定は、元の診断が
消えることと、新しい診断が出ないことの2つである。後者があるため、提案を持つ
事例は「その提案を当てれば通る入力」でなければならない。

位置の有無も別に追跡する。`missing-manifest` と `missing-build` はラベルを
持たず、原因となった記述を示していなかった。依存が多段になると、メッセージ中の
パスだけでは「どの `dowel.toml` の宣言か」が分からない。位置を付けられない
診断は `WITHOUT_LOCATION` に理由とともに記載する。

## テストを足すときの判断

| 何を確かめたいか | 置く場所 |
|---|---|
| 関数・データ構造の振る舞い | 当該クレートの `mod tests` |
| 壊れた入力への耐性 | `robustness.rs` |
| 複数の層をまたぐ組み上げ | `crates/dowel-model/tests/` |
| コンパイラに渡る引数、実際に動く成果物 | `e2e.rs` |
| 編集してからの再実行、構成の切り替え、プロセスを跨いだ変更検出 | `scenario.rs` |
| 実プロジェクトの依存形状でのみ発現する性質 | `tests/projects/` に新しいフィクスチャ |
| 新しい診断 | `diagnostics.rs` の事例表（足さないと網羅検査が落ちる） |
| 新しい文書 | `docs/README.md` の一覧（未記載の場合、文書検査が失敗する） |

## 規約

- テスト名は検査内容を記述する。`test_build` ではなく
  `editing_one_source_recompiles_only_that_object` とする。失敗時に、
  名前から検査対象が判別できる状態にする
- 増分の検査は計数で行う。値の正しさだけでは不十分であり、
  再計算しなかった対象は実行回数でしか観測できない
- 一時ファイルはリポジトリ外に作らず、`target/` 配下に置く
  （`/tmp` を使わない理由は [50-development.md](50-development.md) 5節）
- `examples/` と `tests/projects/` の実体は変更せず、`target/` へ複製してから
  ビルドする。実体に成果物が残った場合は
  `every_fixture_is_left_clean_in_the_repository` が検出する
- コード中の定義は英語で記述する。説明は日本語でよい
  （[50-development.md](50-development.md) 5節）
